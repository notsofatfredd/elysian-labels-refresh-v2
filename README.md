## 2026-08-18 (part J) — fixed live "stuck on load screen" report
- Saeed reported axiel.co.za/elysianlabels stuck on the intro curtain. Pulled the live HTML byte-for-byte and it matched this repo exactly (no stale/broken deploy) — the intro-reveal JS logic (`#introReveal`, `.leaving` → CSS `animationend` → `.done` → `display:none`) was sound but had no failsafe: if `animationend` never fires for any reason (throttled background tab, a blocked/overridden CSS animation, a browser quirk), the curtain had no way to ever remove itself. Added a 2.5s `setTimeout` safety net that force-adds `.done` regardless of whether the animation event fired.
- Also found the Google Fonts `<link rel="stylesheet">` was render-blocking with no fallback — on a slow or blocked connection to `fonts.googleapis.com` (some networks/ad-blockers/regions do this), the browser holds first paint entirely, which looks identical to a stuck load screen since nothing paints, not even the curtain. Switched to the `media="print" onload="this.media='all'"` non-blocking pattern with a `<noscript>` fallback.
- Root cause could not be conclusively reproduced (matched deployed file exactly, so most likely the user's browser had a stale disk-cache hit from before today's upload, or hit one of the two conditions above) — both are now hardened regardless so this class of bug can't recur. **Action needed: re-upload this zip to cPanel** — the fix isn't live until it replaces the currently-deployed files.
- **This did not fix it.** Saeed re-uploaded and it still hung on both desktop and mobile. Reproduced against the live server with a headless Chromium run and found the actual cause: `axiel.co.za` sends `Content-Security-Policy: script-src 'self'` (server/domain-level, not from this repo's `.htaccess`) with no `unsafe-inline`, `nonce`, or hash — this silently blocks execution of every inline `<script>` on the page. Since the whole site was built single-file with all JS inline, **none of it ran on the live server at all**: not theme init, not the curtain-removal code (including the failsafe from the previous fix, which never got the chance to run either), not the burger menu, nothing. The font-swap `onload=""` attribute added in the previous fix was a second, separate CSP violation (inline event handlers are blocked the same way).
- **Actual fix**: extracted all inline JS into `assets/theme-init.js` (head, render-blocking, sets `data-theme` before first paint) and `assets/site.js` (everything else). Both are same-origin external files, so they satisfy `script-src 'self'` with zero change to the CSP itself — no security policy was weakened. Verified by running headless Chromium against a local server sending the identical CSP header: zero console errors, curtain correctly reaches `display:none`.
- Also found and fixed cPanel file permissions were `666` (world-writable) instead of `644` — a security issue independent of the load-screen bug (HTTP serving already worked fine at 666, so this wasn't the cause, but a shared host should never have world-writable site files). This zip's entries have Unix permissions set explicitly (644 files / 755 dirs) so extracting it should restore correct permissions; verify in cPanel File Manager after upload.

## 2026-08-17 (part F) — 3 real bugs, reported by Saeed from an actual device
1. **Mobile header overflow**: `.theme-toggle` had its own `margin-left:var(--s5)` stacked on top of `.hdr-in`'s flex `gap`, double-spacing it from the logo. On narrow phones the cumulative width pushed the burger button past the right edge of the screen (looked like it was "sticking out," present regardless of the nav open/closed state since it's a static layout issue, not an interaction bug). Removed the redundant margin — flex `gap` alone already provides correct spacing.
2. **Invisible "Request Quote" button text** (desktop, visible until hover): pre-existing bug, not introduced this session. `.nav a{color:var(--ink)}` (class+element, specificity 0,1,1) was silently beating `.btn-primary{color:var(--warm-white)}` (single class, specificity 0,1,0) — CSS specificity ignores source order once one selector is more specific. Result: navy text on navy background = invisible, until `:hover`'s higher specificity (0,2,0 vs 0,1,1) briefly won and revealed gold-bg/navy-text. Fixed with a correctly-scoped `.nav a.nav-cta{color:var(--warm-white)}` / `:hover` pair (specificity 0,2,1 / 0,3,1, safely above both). Checked every other `.btn` on the page for the same trap — none of the others sit inside a container with a competing `a{color}` rule, so this was the only instance.
3. **Header logo shows icon only, no wordmark**: `elysian-logo-primary.png` and `elysian-logo-reversed.png` were opened and visually confirmed to be icon-only (just the roll graphic) — despite `ASSET-MANIFEST.md` describing `elysian-logo-primary.png` as "full mark + wordmark." Reverted the text-reconstruction, now both header and footer use the real `elysian-monogram-navy.png` file (footer inverted to white via `.logo-full--footer{filter:brightness(0) invert(1)}`). `elysian-logo-primary.png`/`elysian-logo-reversed.png` are no longer referenced anywhere — left in `assets/` unused rather than deleted, in case they're wanted for something else later.

## 2026-08-17 (part H) — mobile nav dropdown: closed-state text peeking out above the fold
Saeed reported (with a screenshot) the "Solutions" nav link visibly peeking out above the hero content on mobile, burger closed. First attempt added `min-height:0` to `.nav a` (flex items default to `min-height:auto`, a real but secondary contributor). **Still reproduced on Saeed's actual iPhone after that fix and a refresh** — re-reviewed and found the actual primary cause: `.nav{padding:var(--s5);max-height:0;overflow:hidden}` — `max-height` cannot compress a fixed `padding` value, even with `box-sizing:border-box`. `box-sizing:border-box` only changes what the `height`/`max-height` number is measured against; it doesn't make padding negotiable. So the "collapsed" dropdown was never actually 0px — it always rendered at least `2 × var(--s5)` (48px) tall from padding alone, enough to show the first link's text. Real fix: split `padding` into `padding-inline` (always on, doesn't affect the height-collapse problem) and `padding-block` (zeroed in the closed state, restored via `.nav-open{padding-block:var(--s5) !important}` alongside `max-height`). The `min-height:0` from the first attempt stays in as a harmless secondary safeguard.
